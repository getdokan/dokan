# Dokan Admin Dashboard — Precondition Seeding Strategy

> **Goal:** the admin-dashboard spec exercises **admin functionality only**. Every vendor/customer (or system) precondition an admin action needs is seeded via **REST API** (preferred) or **DB** — never by driving the vendor/customer UI.
> **Legend:** API/DB columns — ✅ feasible · 🟡 partial · ❌ not feasible. Recommended — **API** / **DB** / **API+DB** / ⚠️ **UI/gap**.
> Seeding lives in `utils/apiUtils.ts` (REST) and `utils/dbUtils.ts` + `utils/dbData.ts` (DB). Auth contexts: `vendorAuth` / `customerAuth` / admin.

## Summary

- Admin areas analyzed: **15** (0 fully self-contained — no vendor/customer precondition).
- Distinct preconditions identified: **109** — seedable via API ✅ **81**, via DB ✅ **63**, hard gaps ⚠️ **9**.


## Dashboard home (stats / analytics / monthly overview / sales chart / top vendors / most-reviewed / most-reported / notices)

Route: `wp-admin/admin.php?page=dokan-dashboard#/` · _mixed_

The admin Dashboard-home React page reads nine dokan/v1/admin/dashboard/* endpoints whose numbers are all derived from vendor/customer-produced data: completed/processing orders (drive all-time-stats total_sales/total_orders via WC Reports Query, sales-chart daily intervals, top-performing-vendors earning+commission, monthly-overview), commissions in {prefix}_dokan_order_stats joined to {prefix}_wc_order_stats.date_created, vendors (active count + approvals todo), products + WC product reviews with _wc_review_count>0 (most-reviewed-products), pending withdrawals (todo), Pro abuse reports in {prefix}_dokan_report_abuse_reports (most-reported-vendors + monthly abuse trend) and the Pro vendor-metrics. IMPORTANT distinction: nearly every content-level/edge/error/notice/security test in lines 24-70 is explicitly written to MOCK the section endpoint via page.route (DataView padding, trend math, currency formatting, skeleton, 500 error boxes, the entire AdminNotices slider/modal, XSS guards, malformed-date 400) — those need NO seeded data. Real seeded preconditions are only needed for the genuine end-to-end happy paths that assert against live numbers (P1 ordered-headings/content render, real top-vendor rows, real all-time-stats currency, real monthly-overview comparison, real sales-chart points, real most-reviewed rows, the show_most_reported_vendors gate) and the @pro Vendor Metrics / Most Reported gating. Everything seedable lies upstream of admin UI: create vendor(s) -> product(s) -> place+complete customer orders (API), then for month-comparison BACK-DATE the order_stats rows (DB), seed product reviews (API), abuse reports (DB), and a withdrawal (API). Admin notices and the is_pro_exists/show_most_reported_vendors flags are PHP/option-driven, not vendor/customer data — handle via route-mock or option/DB toggle. Prefer DB-backed dates because no API can set wc_order_stats.date_created to a prior month deterministically.

## Vendors list & vendor states

Route: `#/vendors (wp-admin/admin.php?page=dokan-dashboard#/vendors)` · _mixed_

Not self-contained: this admin list IS about vendor state, so every meaningful test needs vendors that already exist in specific states (approved/enabled, disabled/pending, with/without store categories, with/without phone, with a registration date to sort on). All of these are seedable via API with the admin-auth store helpers (createStore + updateStoreStatus/updateStore/batch), with a DB fallback via dokan_enable_selling user meta and a DB-only path for back-dating user_registered. Approve/Disable actions and the empty/security/a11y cases are admin-only mutations that just need the right pre-seeded vendors. Pro store categories are seedable via API by passing categories:[{id}] (after creating the term with createStoreCategory); vendor switching switch_url is a settings/admin-session affordance, not a vendor/customer data precondition.

## Vendor single (detail)

Route: `#/vendors/:id` · _mixed_

Not self-contained: the admin vendor-single page only renders/edits admin-side, but its content is fed by vendor/customer-produced data. Everything required is API-seedable (admin auth) before the spec runs. The single createStore call (payloads.createStore) bundles most preconditions at once: it creates the seller user + store and sets featured, enabled, trusted, payment/withdraw methods (paypal/bank/skrill/dokan_custom), social links, full address, store categories[], and admin commission type/amount. Beyond that you need: products owned by the vendor (Overview top-products + Pro Total Products), completed customer orders against those products (drives current balance, total earning, item-sold, and the top-selling-products grid), store reviews (HeaderCard Rating + ratings/reviews; Pro store-reviews module), and a separate fresh/empty vendor for the empty-state/placeholder negative+edge cases. Order placement and balance are the only partials: WC orders always run under adminAuth (fine), but vendor balance/earning cannot be set directly via REST and must be induced by completing an order on a vendor-owned product (createOrderWithStatus '... wc-completed'), or back-dated/forced via DB if a specific amount/date is needed.

## Withdraw (admin approve / cancel / pay)

Route: `#/withdraw` · _mixed_

The admin WithdrawPage (#/withdraw, dokan/v2/withdraw) is a pure moderation surface: every row is a VENDOR-created withdrawal request, so the spec must programmatically seed vendor requests in each status (pending/approved/cancelled), the vendor available balance that backs them, and an active vendor payment method (PayPal/bank/skrill, plus the Pro dokan_custom method) before exercising approve/cancel/delete/add-note/view/export. All preconditions are API-seedable, mirroring the existing new-withdraw spec helpers (seedPendingWithdraw/seedApprovedWithdraw). Three hard ordering constraints: (1) a payment method must be active or createWithdraw 400s with "Withdraw method is not active"; (2) the vendor balance must clear the minimum withdraw limit (seed via a wc-completed order) or createWithdraw 400s and admin Approve hits the insufficient-balance guard; (3) the REST create_item ALWAYS forces status=pending and rejects a 2nd pending request per vendor, so approved/cancelled rows require create-pending-then-PUT (or batch). DB seeding (dbUtils.dbQuery into {prefix}dokan_withdraw) is the recommended fallback for forcing the insufficient-balance state, back-dating dates for the Date Range filter, and seeding bulk/perf datasets without the one-pending-per-vendor limit.
