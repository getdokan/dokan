# Abuse Reports — Test Cases & Edge Cases

Scope: the new React admin page (`ReportAbusePage.tsx` mounted at `/wp-admin/admin.php?page=dokan-dashboard#/abuse-reports`), the REST controller (`dokan/v1/abuse-reports*`), the front-end report flow on single-product pages, and the admin settings under `Settings → Product Report Abuse`.

Conventions:
- **A** = admin (`administrator`)
- **V1 / V2** = vendors (`seller`)
- **C1 / C2** = customers (`customer`)
- **G** = guest / unauthenticated
- "Module" refers to the *Report Abuse* module under Dokan Pro modules
- "Setting A" = `Settings → Product Report Abuse → Reported by → Only logged-in users can report` (toggle)
- "Setting B" = `Settings → Product Report Abuse → Reasons for Abuse Report` (repeatable list)
- "List" = the React DataViews table on the admin page
- "Detail modal" = the modal that opens when clicking a row's reason or "View" action
- "Delete modal" = the confirmation modal for delete

## 11. Suggested Playwright e2e additions (beyond the existing `abuseReports.spec.ts` cases 1–6)

These map directly to gaps above and are good follow-ups once core stability lands:

1. **Bulk delete from the new dashboard list** — select N rows, confirm modal, assert toast + table rows decreased by N.
2. **Filter persistence across pagination** — apply reason filter, paginate to page 2, verify filter chip still present and request params include it.
3. **Filter combinations** — reason + vendor + product, verify only intersecting reports are listed.
4. **Detail modal content** — open via reason cell click *and* "View" action; assert reason, description, product link, vendor link, reported-by, and `DateTimeHtml` text.
5. **Anonymous report end-to-end** — disable Setting A, submit as guest, log in as admin, verify the row shows "Anonymous" and no admin URL.
6. **Setting A enforcement on front-end** — enable Setting A, attempt guest submit, assert error in popup.
7. **Reason-rename dangling state** — submit report with reason "X" → rename to "Y" in settings → verify the row still displays "X" and the filter dropdown only offers "Y".
8. **REST permission boundary** — vendor token GETs `/abuse-reports`; if the team confirms it should be admin-only, this becomes a regression test once the `is_dokandar` check is tightened.
9. **Pagination off-by-one** — set `per_page=5`, seed 12 reports, navigate to page 3, assert 2 rows (and the `X-Dokan-AbuseReports-TotalPages` header value).
10. **RawHTML safety** — submit a report whose reason contains a `<script>` tag; assert the script does not execute when the table cell is rendered (current implementation is *vulnerable* — this test should fail until sanitization is added).

## 12. Known issues / regressions to watch (developer-facing)

These came out of reading the code; they're not test cases per se but should drive defensive tests:

- **`is_dokandar` permission** in `RestController.php` lets vendors hit admin endpoints (likely a copy-paste leftover; should be `current_user_can('manage_options')` or a dedicated cap).
- **Hard-coded `per_page = 20`** in `RestController::get_items` for the `X-Dokan-AbuseReports-TotalPages` calculation will mis-report total pages if the React UI sends `per_page=50` (which it will once the user changes page size in DataViews).
- **RawHTML rendering** of unsanitized reason/description in `ReportAbusePage.tsx` is XSS-unsafe.
- **Reason filter mismatch** — the React UI sends the reason *label* to the API (`filter.reason = selectedOption.label`), and the SQL also matches on label. Any future change that sends `id` instead silently breaks all reports.
- **Product / vendor missing → silent skip** in `dokan_report_abuse_get_reports` causes the response array length to disagree with `X-Dokan-AbuseReports-Total` (count query doesn't filter by product existence).
- **Pluralization** in delete confirmation copy: `"these %d abuse report?"` should be `"reports?"`.
- **Toast import** — the page imports `useToast` and `DokanToaster` from `@getdokan/dokan-ui` *and* renders `DokanToaster` itself; if the admin shell already mounts a toaster, you'll get duplicate toasters and double-fired messages.
- **Mismatched text domains** — most strings use `'dokan'`, but the AdminFilter field labels use `'dokan-lite'`.
